# REGLAS CRÍTICAS DEL PROYECTO: Sistema de Inventario Chamalú Beer

Estas reglas tienen prioridad sobre cualquier otra instrucción de la tarea.
Si una tarea entra en conflicto con ellas, DETENTE y avísame antes de continuar.

## 1. Flujo de trabajo
- Antes de modificar cualquier cosa, muéstrame un PLAN: qué archivos vas a tocar, qué vas a cambiar y por qué.
- Espera mi aprobación explícita antes de escribir o modificar código.
- Trabaja por pasos pequeños y dime qué hiciste al terminar cada uno.
- Código básico, fácil de leer y con comentarios. No agregues archivos o dependencias complejas sin preguntarme.

## 2. Base de datos (CRÍTICO: los datos reales del bar no se pueden perder)
- NUNCA copies, reemplaces, borres, renombres ni recrees archivos .db (data/chamalu.db).
- NUNCA subas archivos .db a git ni los incluyas en ningún despliegue o release.
- Los cambios de estructura (tablas o columnas nuevas) se hacen SOLO con migraciones en la carpeta /migrations, numeradas (001_, 002_...), que modifican la base existente y se ejecutan una sola vez al arrancar el servidor.
- Las migraciones deben ser seguras: usar CREATE TABLE IF NOT EXISTS y ALTER TABLE, sin DROP ni DELETE sobre datos existentes.
- Nunca restaures una base "vieja" o de otra versión sobre la actual.
- Prueba siempre con una base separada (data/dev.db), nunca con la de producción. La ruta se lee de la variable de entorno DB_PATH.
- Si una tarea implica tocar, borrar o transformar datos existentes, detente y pídeme aprobación.

## 3. Respaldos
- Antes de cualquier despliegue, migración o cambio que pueda afectar datos, crea una copia en /backups con fecha y hora (ej. chamalu-20261028-153000.db).
- Confírmame que el respaldo existe antes de continuar.

## 4. Versiones
- La única fuente de la versión es package.json. Nunca escribas una versión a mano ni la repitas en otros archivos.
- NUNCA reutilices una versión ya publicada (ej. 2.0.0).
- Antes de publicar: ejecuta `git tag -l`, lee la última versión y propónme la siguiente (patch, minor o major) con una razón. Espera mi aprobación.
- Sube la versión con `npm version patch|minor|major` y publica solo con release.sh.
- Si el tag ya existe, detente y avísame.

## 5. Tareas pendientes (hazlas solo después de mi aprobación del plan)
1. Agregar al .gitignore: data/*.db, data/*.db-wal, data/*.db-shm. Si el .db estaba en git, quitarlo del seguimiento con `git rm --cached` sin borrar el archivo.
2. Crear la carpeta /migrations y el mecanismo que registra qué migraciones ya se aplicaron.
3. Configurar DB_PATH (por defecto data/dev.db en desarrollo).
4. Crear release.sh con respaldo automático y verificación de tag duplicado.
